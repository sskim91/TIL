# 효과적인 에이전트 구축하기

> 이 글은 [Anthropic Engineering](https://www.anthropic.com/engineering)의 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 를 한국어로 번역한 글입니다.
> 원문 작성일: 2024년 12월 19일 | 작성자: Erik Schluntz, Barry Zhang

지난 1년간 Anthropic은 다양한 산업에서 LLM(Large Language Model) 에이전트를 구축하는 수십 개의 팀과 협력했다. 가장 성공적인 구현들은 복잡한 프레임워크나 전문 라이브러리를 사용하지 않았다. 대신, **단순하고 조합 가능한 패턴** 으로 구축하고 있었다.

이 글에서는 고객들과 협력하고 직접 에이전트를 구축하면서 배운 것들을 공유하고, 효과적인 에이전트를 만들기 위한 실용적인 조언을 제공한다.

## 에이전트란 무엇인가?

"에이전트"는 여러 방식으로 정의될 수 있다. 어떤 고객은 에이전트를 장시간 독립적으로 작동하며 다양한 도구를 사용해 복잡한 작업을 수행하는 완전 자율 시스템으로 정의한다. 다른 고객들은 미리 정의된 워크플로우를 따르는 좀 더 규범적인 구현을 에이전트라고 부른다. Anthropic에서는 이 모든 변형을 **에이전틱 시스템(agentic systems)** 으로 분류하되, 아키텍처적으로 중요한 구분을 둔다:

- **워크플로우(Workflows):** LLM과 도구가 **미리 정의된 코드 경로** 를 통해 오케스트레이션되는 시스템
- **에이전트(Agents):** LLM이 자신의 프로세스와 도구 사용을 **동적으로 지시** 하며, 작업 수행 방법에 대한 제어권을 유지하는 시스템

아래에서 두 유형의 에이전틱 시스템을 자세히 살펴본다. 부록 1("에이전트의 실전 활용")에서는 고객들이 특히 가치를 발견한 두 가지 분야를 설명한다.

## 에이전트를 사용해야 할 때 (그리고 사용하지 말아야 할 때)

LLM을 활용한 애플리케이션을 구축할 때, **가능한 한 가장 단순한 솔루션을 찾고** 필요할 때만 복잡성을 높이는 것을 권장한다. 이는 에이전틱 시스템을 아예 구축하지 않는 것을 의미할 수도 있다. 에이전틱 시스템은 종종 **더 나은 작업 성능을 위해 지연 시간과 비용을 교환** 하는 것이며, 이 트레이드오프가 합리적인 시점을 고려해야 한다.

더 높은 복잡성이 필요한 경우, 워크플로우는 잘 정의된 작업에 대한 예측 가능성과 일관성을 제공하는 반면, 에이전트는 유연성과 모델 주도 의사결정이 대규모로 필요한 경우에 더 나은 선택이다. 그러나 많은 애플리케이션에서는 검색과 in-context 예시를 활용한 단일 LLM 호출 최적화만으로 충분하다.

## 프레임워크를 언제, 어떻게 사용할 것인가

에이전틱 시스템 구현을 쉽게 만들어주는 많은 프레임워크가 있다:

- Claude Agent SDK
- AWS의 Strands Agents SDK
- Rivet - 드래그 앤 드롭 GUI LLM 워크플로우 빌더
- Vellum - 복잡한 워크플로우를 구축하고 테스트하는 GUI 도구

이 프레임워크들은 LLM 호출, 도구 정의 및 파싱, 호출 체이닝 같은 표준적인 저수준 작업을 단순화하여 시작하기 쉽게 만든다. 그러나 **추가적인 추상화 계층을 생성** 하여 기저의 프롬프트와 응답을 불투명하게 만들고, 디버깅을 어렵게 할 수 있다. 또한 더 단순한 구성이 충분한 상황에서 불필요한 복잡성을 추가하고 싶은 유혹을 줄 수 있다.

개발자가 LLM API를 직접 사용하는 것부터 시작하는 것을 권장한다. 많은 패턴이 몇 줄의 코드로 구현될 수 있다. 프레임워크를 사용하더라도 기저 코드를 이해해야 한다. 내부 동작에 대한 잘못된 가정이 흔한 오류의 원인이다.

## 빌딩 블록, 워크플로우, 그리고 에이전트

이 섹션에서는 프로덕션에서 볼 수 있는 에이전틱 시스템의 일반적인 패턴을 살펴본다. 기본 빌딩 블록인 증강된 LLM(augmented LLM)부터 시작하여, 단순한 조합형 워크플로우에서 자율 에이전트까지 점진적으로 복잡성을 높여간다.

### 빌딩 블록: 증강된 LLM (Augmented LLM)

에이전틱 시스템의 기본 빌딩 블록은 **검색(retrieval), 도구(tools), 메모리(memory)** 같은 기능으로 강화된 LLM이다. 현재의 모델들은 이러한 기능을 능동적으로 사용할 수 있다 — 자체적으로 검색 쿼리를 생성하고, 적절한 도구를 선택하고, 어떤 정보를 유지할지 결정한다.

![The augmented LLM](https://cdn.sanity.io/images/4zrzovbb/website/d3083d3f40bb2b6f477901cc9a240738d3dd1371-2401x1000.png)

구현에서 두 가지 핵심 측면에 집중하는 것을 권장한다:

1. 이러한 기능을 **특정 사용 사례에 맞게 조정** 하는 것
2. LLM에 **쉽고 잘 문서화된 인터페이스** 를 제공하는 것

이러한 기능을 구현하는 방법은 여러 가지가 있지만, 한 가지 접근 방식은 Model Context Protocol(MCP)을 사용하는 것이다. MCP는 개발자가 간단한 클라이언트 구현으로 점점 확장되는 서드파티 도구 생태계와 통합할 수 있게 해준다.

### 워크플로우: 프롬프트 체이닝 (Prompt Chaining)

프롬프트 체이닝(Prompt chaining)은 작업을 일련의 단계로 분해하며, 각 LLM 호출이 이전 호출의 출력을 처리한다. 프로세스가 올바른 방향으로 진행되고 있는지 확인하기 위해 중간 단계에 프로그래밍적 검사("게이트")를 추가할 수 있다.

![The prompt chaining workflow](https://cdn.sanity.io/images/4zrzovbb/website/7418719e3dab222dccb379b8879e1dc08ad34c78-2401x1000.png)

**사용 시기:** 작업이 고정된 하위 작업으로 쉽고 깔끔하게 분해될 수 있는 상황에 적합하다. 주요 목표는 각 LLM 호출을 더 쉬운 작업으로 만들어 **정확도를 높이는 대신 지연 시간을 교환** 하는 것이다.

**프롬프트 체이닝이 유용한 예시:**

- 마케팅 카피를 생성한 후, 다른 언어로 번역
- 문서의 아웃라인을 작성하고, 아웃라인이 특정 기준을 충족하는지 확인한 다음, 아웃라인을 기반으로 문서 작성

### 워크플로우: 라우팅 (Routing)

라우팅(Routing)은 입력을 분류하고 전문화된 후속 작업으로 전달한다. 이 워크플로우는 **관심사의 분리** 를 가능하게 하고, 더 전문화된 프롬프트를 구축할 수 있게 한다. 이 워크플로우 없이는 한 종류의 입력에 최적화하면 다른 입력의 성능이 저하될 수 있다.

![The routing workflow](https://cdn.sanity.io/images/4zrzovbb/website/5c0c0e9fe4def0b584c04d37849941da55e5e71c-2401x1000.png)

**사용 시기:** 별도로 처리하는 것이 더 나은 뚜렷한 카테고리가 있는 복잡한 작업에 적합하며, LLM이나 전통적인 분류 모델/알고리즘으로 분류를 정확하게 처리할 수 있는 경우에 좋다.

**라우팅이 유용한 예시:**

- 다양한 유형의 고객 서비스 쿼리(일반 문의, 환불 요청, 기술 지원)를 서로 다른 다운스트림 프로세스, 프롬프트, 도구로 라우팅
- 쉽거나 일반적인 질문은 비용 효율적인 소형 모델(Claude Haiku 4.5)로, 어렵거나 특이한 질문은 더 능력 있는 모델(Claude Sonnet 4.5)로 라우팅하여 성능 최적화

### 워크플로우: 병렬화 (Parallelization)

LLM이 때로는 작업을 동시에 처리하고 그 출력을 프로그래밍적으로 집계할 수 있다. 이 병렬화(Parallelization) 워크플로우는 두 가지 주요 변형으로 나타난다:

- **구획화(Sectioning):** 작업을 독립적인 하위 작업으로 나누어 병렬로 실행
- **투표(Voting):** 같은 작업을 여러 번 실행하여 다양한 출력을 획득

![The parallelization workflow](https://cdn.sanity.io/images/4zrzovbb/website/406bb032ca007fd1624f261af717d70e6ca86286-2401x1000.png)

**사용 시기:** 나뉜 하위 작업이 속도를 위해 병렬화될 수 있거나, 더 높은 신뢰도를 위해 여러 관점이나 시도가 필요한 경우에 효과적이다. 복잡한 작업에서 여러 고려사항이 있을 때, LLM은 일반적으로 각 고려사항을 별도의 LLM 호출로 처리할 때 더 좋은 성능을 보인다.

**구획화가 유용한 예시:**

- 하나의 모델 인스턴스가 사용자 쿼리를 처리하고 다른 인스턴스가 부적절한 콘텐츠를 스크리닝하는 가드레일 구현. 같은 LLM 호출이 가드레일과 핵심 응답을 동시에 처리하는 것보다 성능이 더 좋다.
- LLM 성능 평가 자동화에서 각 LLM 호출이 주어진 프롬프트에 대한 모델 성능의 서로 다른 측면을 평가

**투표가 유용한 예시:**

- 코드의 취약점을 리뷰할 때, 여러 다른 프롬프트가 코드를 검토하고 문제 발견 시 플래그
- 주어진 콘텐츠가 부적절한지 평가할 때, 여러 프롬프트가 서로 다른 측면을 평가하거나 다른 투표 임계값을 요구하여 오탐과 미탐의 균형을 맞춤

### 워크플로우: 오케스트레이터-워커 (Orchestrator-Workers)

오케스트레이터-워커(Orchestrator-workers) 워크플로우에서는 중앙 LLM이 동적으로 작업을 분해하고, 워커 LLM에 위임하며, 결과를 종합한다.

![The orchestrator-workers workflow](https://cdn.sanity.io/images/4zrzovbb/website/8985fc683fae4780fb34eab1365ab78c7e51bc8e-2401x1000.png)

**사용 시기:** 필요한 하위 작업을 미리 예측할 수 없는 복잡한 작업에 적합하다. 병렬화와의 핵심 차이점은 유연성이다 — 하위 작업이 미리 정의되지 않고, 특정 입력에 기반하여 오케스트레이터가 결정한다.

**유용한 예시:**

- 매번 여러 파일에 복잡한 변경을 가하는 코딩 제품
- 관련 가능성이 있는 정보를 위해 여러 소스에서 정보를 수집하고 분석하는 검색 작업

### 워크플로우: 평가자-최적화기 (Evaluator-Optimizer)

평가자-최적화기(Evaluator-optimizer) 워크플로우에서는 하나의 LLM 호출이 응답을 생성하고, 다른 LLM이 루프 내에서 평가와 피드백을 제공한다.

![The evaluator-optimizer workflow](https://cdn.sanity.io/images/4zrzovbb/website/14f51e6406ccb29e695da48b17017e899a6119c7-2401x1000.png)

**사용 시기:** 명확한 평가 기준이 있고, 반복적인 개선이 측정 가능한 가치를 제공하는 경우에 특히 효과적이다. 적합성을 나타내는 두 가지 신호:

1. 인간이 피드백을 명확히 표현할 때 LLM 응답이 개선될 수 있는 경우
2. LLM이 그러한 피드백을 제공할 수 있는 경우

이는 인간 작가가 완성된 문서를 만들기 위해 거치는 반복적 글쓰기 과정과 유사하다.

**유용한 예시:**

- 번역 LLM이 처음에 포착하지 못할 수 있는 뉘앙스가 있지만, 평가자 LLM이 유용한 비평을 제공할 수 있는 **문학 번역**
- 종합적인 정보를 수집하기 위해 여러 라운드의 검색과 분석이 필요한 **복잡한 검색 작업** 에서, 평가자가 추가 검색이 필요한지 결정

### 에이전트 (Agents)

에이전트는 LLM이 핵심 역량에서 성숙해짐에 따라 프로덕션에서 등장하고 있다 — 복잡한 입력 이해, 추론과 계획, 도구의 신뢰성 있는 사용, 오류 복구. 에이전트는 인간 사용자의 명령이나 대화적 논의로부터 작업을 시작한다. 작업이 명확해지면, 에이전트는 독립적으로 계획하고 실행하며, 필요시 추가 정보나 판단을 위해 인간에게 돌아올 수 있다.

![Autonomous agent](https://cdn.sanity.io/images/4zrzovbb/website/58d9f10c985c4eb5d53798dea315f7bb5ab6249e-2401x1000.png)

실행 중에, 에이전트가 각 단계에서 환경으로부터 **"지상 진실(ground truth)"** 을 획득하는 것이 중요하다 (도구 호출 결과나 코드 실행 등). 에이전트는 체크포인트나 차단 상황에서 인간의 피드백을 위해 일시 정지할 수 있다. 작업은 완료 시 종료되는 것이 일반적이지만, 제어를 유지하기 위해 정지 조건(최대 반복 횟수 등)을 포함하는 것도 흔하다.

에이전트는 정교한 작업을 처리할 수 있지만, 구현은 종종 간단하다. 일반적으로 **루프 내에서 환경 피드백에 기반하여 도구를 사용하는 LLM** 에 불과하다. 따라서 도구 세트와 그 문서를 명확하고 신중하게 설계하는 것이 매우 중요하다. 부록 2("도구를 프롬프트 엔지니어링하기")에서 도구 개발 모범 사례를 더 자세히 다룬다.

**사용 시기:** 필요한 단계 수를 예측하기 어렵거나 불가능한 **개방형 문제** 에서, 고정된 경로를 하드코딩할 수 없는 경우에 사용한다. LLM이 잠재적으로 많은 턴 동안 작동할 것이며, 그 의사결정에 어느 정도의 신뢰가 있어야 한다. 에이전트의 자율성은 신뢰할 수 있는 환경에서 작업을 확장하는 데 이상적이다.

에이전트의 자율적 특성은 **더 높은 비용** 과 **오류 누적 가능성** 을 의미한다. 샌드박스 환경에서의 광범위한 테스트와 적절한 가드레일을 권장한다.

**유용한 예시:**

- 작업 설명에 기반하여 많은 파일을 편집하는 SWE-bench 작업을 해결하는 **코딩 에이전트**
- Claude가 컴퓨터를 사용하여 작업을 수행하는 **"computer use" 레퍼런스 구현**

## 이러한 패턴의 조합과 커스터마이징

이 빌딩 블록들은 규범적이지 않다. 개발자가 다양한 사용 사례에 맞게 형태를 만들고 조합할 수 있는 **일반적인 패턴** 이다. 성공의 핵심은 모든 LLM 기능과 마찬가지로 **성능을 측정하고 구현을 반복** 하는 것이다. 복잡성은 결과를 명확히 개선할 때 **만** 추가해야 한다.

## 요약

LLM 영역에서의 성공은 가장 정교한 시스템을 구축하는 것이 아니다. **필요에 맞는 올바른 시스템** 을 구축하는 것이다. 단순한 프롬프트로 시작하고, 포괄적인 평가로 최적화하며, 단순한 솔루션으로 부족할 때만 멀티스텝 에이전틱 시스템을 추가하라.

에이전트를 구현할 때 따르는 세 가지 핵심 원칙:

1. 에이전트 설계에서 **단순성(simplicity)** 을 유지하라.
2. 에이전트의 계획 단계를 명시적으로 보여주어 **투명성(transparency)** 을 우선시하라.
3. 철저한 도구 **문서화와 테스트(documentation and testing)** 를 통해 에이전트-컴퓨터 인터페이스(ACI)를 신중하게 설계하라.

프레임워크는 빠르게 시작하는 데 도움이 될 수 있지만, 프로덕션으로 이동할 때는 추상화 계층을 줄이고 기본 컴포넌트로 구축하는 것을 주저하지 마라. 이러한 원칙을 따르면 강력할 뿐만 아니라 신뢰할 수 있고, 유지보수 가능하며, 사용자에게 신뢰받는 에이전트를 만들 수 있다.

### 감사의 말

이 글은 Erik Schluntz와 Barry Zhang이 작성했다. 이 작업은 Anthropic에서의 에이전트 구축 경험과 고객들이 공유한 귀중한 인사이트를 바탕으로 한다.

## 부록 1: 에이전트의 실전 활용

Anthropic의 고객 협업을 통해 AI 에이전트의 두 가지 특히 유망한 응용 분야가 드러났다. 두 응용 분야 모두 에이전트가 가장 큰 가치를 더하는 작업의 특성을 보여준다: **대화와 행동이 모두 필요** 하고, **명확한 성공 기준** 이 있으며, **피드백 루프** 가 가능하고, **의미 있는 인간 감독** 이 통합된 작업이다.

### A. 고객 지원

고객 지원은 친숙한 챗봇 인터페이스와 도구 통합을 통한 향상된 기능을 결합한다. 더 개방형 에이전트에 자연스럽게 적합한 이유:

- 지원 상호작용은 자연스럽게 대화 흐름을 따르면서 외부 정보와 행동에 대한 접근이 필요
- 고객 데이터, 주문 이력, 지식 베이스 문서를 가져오는 도구 통합 가능
- 환불 발행이나 티켓 업데이트 같은 행동을 프로그래밍적으로 처리 가능
- 성공을 사용자 정의 해결을 통해 명확히 측정 가능

여러 회사가 성공적인 해결에 대해서만 과금하는 사용량 기반 가격 모델을 통해 이 접근 방식의 실행 가능성을 입증했다.

### B. 코딩 에이전트

소프트웨어 개발 분야는 코드 완성에서 자율적 문제 해결까지 기능이 진화하며 놀라운 잠재력을 보여주었다. 에이전트가 특히 효과적인 이유:

- 코드 솔루션이 자동화된 테스트로 검증 가능
- 에이전트가 테스트 결과를 피드백으로 사용하여 솔루션을 반복 가능
- 문제 공간이 잘 정의되고 구조화됨
- 출력 품질을 객관적으로 측정 가능

![High-level flow of a coding agent](https://cdn.sanity.io/images/4zrzovbb/website/4b9a1f4eb63d5962a6e1746ac26bbc857cf3474f-2400x1666.png)

Anthropic 자체 구현에서, 에이전트는 이제 pull request 설명만으로 SWE-bench Verified 벤치마크의 실제 GitHub 이슈를 해결할 수 있다. 그러나 자동화된 테스트가 기능 검증에 도움이 되지만, 솔루션이 더 넓은 시스템 요구사항과 일치하는지 확인하기 위해 **인간의 리뷰는 여전히 필수적** 이다.

## 부록 2: 도구를 프롬프트 엔지니어링하기

어떤 에이전틱 시스템을 구축하든, 도구는 에이전트의 중요한 부분이 될 것이다. 도구는 Claude가 API에서 정확한 구조와 정의를 지정하여 외부 서비스 및 API와 상호작용할 수 있게 한다. Claude가 응답할 때, 도구를 호출할 계획이 있으면 API 응답에 tool use 블록을 포함한다. **도구의 정의와 사양에는 전체 프롬프트와 동일한 수준의 프롬프트 엔지니어링 관심을 기울여야 한다.**

같은 행동을 지정하는 여러 방법이 있다. 예를 들어, 파일 편집을 diff로 지정하거나 전체 파일을 다시 쓸 수 있다. 구조화된 출력의 경우, 코드를 markdown 내부나 JSON 내부에 반환할 수 있다. 소프트웨어 엔지니어링에서 이런 차이는 외견상의 것이며 서로 손실 없이 변환할 수 있다. 그러나 **일부 형식은 LLM이 작성하기 훨씬 더 어렵다.** diff를 작성하려면 새 코드가 작성되기 전에 청크 헤더에서 변경되는 줄 수를 알아야 한다. JSON 내부에 코드를 작성하면(markdown과 비교하여) 줄바꿈과 따옴표에 대한 추가 이스케이핑이 필요하다.

도구 형식을 결정하기 위한 제안은 다음과 같다:

- 모델이 스스로를 궁지에 몰아넣기 전에 "생각할" 충분한 토큰을 제공하라.
- 모델이 인터넷의 텍스트에서 자연스럽게 접하는 것에 가까운 형식을 유지하라.
- 수천 줄의 코드에 대한 정확한 카운트 유지나 작성하는 코드의 문자열 이스케이핑 같은 형식적 "오버헤드"가 없도록 하라.

하나의 경험 법칙은 인간-컴퓨터 인터페이스(HCI)에 얼마나 많은 노력이 투입되는지 생각하고, **에이전트-컴퓨터 인터페이스(ACI)** 를 만드는 데도 동일한 수준의 노력을 투자할 계획을 세우는 것이다. 이를 위한 몇 가지 생각은 다음과 같다:

- **모델의 입장에서 생각하라.** 설명과 매개변수를 기반으로 이 도구를 사용하는 방법이 명확한가? 아니면 신중하게 생각해야 하는가? 그렇다면 모델에게도 마찬가지다. 좋은 도구 정의에는 사용 예시, 엣지 케이스, 입력 형식 요구사항, 다른 도구와의 명확한 경계가 포함된다.
- **매개변수 이름이나 설명을 어떻게 바꾸면 더 명확해질까?** 팀의 주니어 개발자를 위한 훌륭한 독스트링을 작성한다고 생각하라. 유사한 도구가 많을 때 특히 중요하다.
- **모델이 도구를 어떻게 사용하는지 테스트하라.** 워크벤치에서 많은 예시 입력을 실행하여 모델이 어떤 실수를 하는지 확인하고 반복하라.
- **포카요케(Poka-yoke) 원칙을 도구에 적용하라.** 실수하기 어렵도록 인수를 변경하라.

SWE-bench용 에이전트를 구축할 때, 실제로 전체 프롬프트보다 **도구를 최적화하는 데 더 많은 시간** 을 썼다. 예를 들어, 에이전트가 루트 디렉토리 밖으로 이동한 후 상대 경로를 사용하는 도구에서 실수를 하는 것을 발견했다. 이를 수정하기 위해 도구를 항상 **절대 경로를 요구** 하도록 변경했고, 모델이 이 방법을 완벽하게 사용하는 것을 확인했다.
